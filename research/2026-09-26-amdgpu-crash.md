# AMDGPU desktop crash

## Local evidence

Incident: 2026-09-25, approximately 23:24:41 EDT. Previous boot ID:
`9d7da3db734b4d5dbedfd193dd4d8396`. Read-only inspection used the kernel journal,
selected system events, PCI mapping, coredump metadata, and the Hyprland crash
report header/renderer backtrace. No browser profiles or core-memory contents
were read. Narrow evidence is retained privately under
`~/.local/state/dotfiles-migration/20260926T031447Z/` as `crash-kernel.log`,
`crash-timeline.log`, and `crash-gpu-mapping.txt`; build/check logs are alongside.
The Hyprland report is `~/.cache/hyprland/hyprlandCrashReport50065.txt`.

This is a postmortem, not a reproduced or fixed defect. Deliberately reproducing
a GPU hang could destroy the current desktop session, so no crash/stress test
was attempted. The current boot showed no matching GPU timeout at inspection.

## Findings
- **The available local record identifies the integrated GPU, not the RX 9060 XT, as the timed-out device.** It records `amdgpu 0000:14:00.0: ring gfx_0.0.0 timeout`; `14:00.0` is the Raphael iGPU, while the discrete Navi44 is `03:00.0`. The record also places the affected browser GPU thread in the timeout report, then records a failed per-ring reset and a successful MODE2 recovery. Source: the captured `crash-kernel.log` and `crash-gpu-mapping.txt` described above.
- **This is a GPU job timeout with recovery, not evidence of an OOM, kernel panic, or dGPU fault.** In Linux v6.18, the AMDGPU scheduler logs a ring timeout, looks up and prints task information for the job PASID, tries a per-ring reset, then starts GPU recovery if that fails. This matches the reported ordering of the browser thread, ring-reset failure, and GPU reset. It associates the browser with the timed-out job; it does not prove that browser code, Mesa, Hyprland, hardware, or the browser caused the hang. Source: [Linux v6.18 `amdgpu_job.c`](https://github.com/torvalds/linux/blob/v6.18/drivers/gpu/drm/amd/amdgpu/amdgpu_job.c).
- **“Full MODE2 recovery” means escalation beyond a queue/ring reset, not necessarily a reset of every ASIC component.** Linux labels MODE2 as a reset of a lesser set of IP blocks than MODE1; the selected blocks are ASIC-specific and MODE2 notably avoids CPU-shared IPs on APUs and memory controllers. The reported success proves the kernel restored enough of the iGPU to continue; it does not establish a hardware reset, isolate a failed block, or validate the post-reset graphics stack. Source: [Linux v6.18 `amdgpu.h`, `enum amd_reset_method`](https://github.com/torvalds/linux/blob/v6.18/drivers/gpu/drm/amd/amdgpu/amdgpu.h#L437-L475).
- **The trailing graphical-client failures are temporally downstream, not a demonstrated root cause.** The supplied sequence has live Hyprland aborting in its GL renderer, then the browser core and other graphical clients failing after recovery. The compositor report shows a GL-renderer abort, consistent with failure after the device reset. That stack does not identify why the earlier GPU job hung. Sources: captured journal timeline, coredump metadata, and the Hyprland renderer backtrace described above.
- **`parser -125` is insufficient to classify the incident.** Linux defines error 125 as `ECANCELED` (“Operation Canceled”), but without the log line’s emitting component and surrounding context it does not identify a malformed command stream, firmware failure, or the origin of the hang. Source: [Linux v6.18 generic errno definitions](https://github.com/torvalds/linux/blob/v6.18/include/uapi/asm-generic/errno.h#L110-L114).
- **The interrupted dotfiles migration is not supported as the cause.** The supplied evidence says the build completed before the incident, evaluation checks stopped before application validators, no activation ran, and the running system was unchanged. The three evaluation warnings were earlier and do not connect to the iGPU timeout. This rules out that migration from having applied a GPU configuration change; it cannot rule out unrelated runtime defects merely by timing. Sources: `build.log`, `check.log`, `built-system.txt`, captured journal timeline, and the unchanged `/run/current-system` identity.
- **Use PCI identity, not `/dev/dri/cardN`, for any GPU decision.** Hyprland’s official multi-GPU guide says card numbers are dynamically assigned at boot, describes `/dev/dri/by-path` PCI mappings, and recommends stable udev symlinks where a colon-separated `AQ_DRM_DEVICES` value needs a stable name. Source: [Hyprland wiki source: Multi-GPU](https://github.com/hyprwm/hyprland-wiki/blob/main/content/configuring/extra/multi-gpu.md).
- **A browser-only dGPU experiment is technically bounded but not yet evidence-based.** Mesa documents `DRI_PRIME=pci-0000_03_00_0` as selecting that PCI GPU for OpenGL and placing it first for Vulkan; appending `!` exposes only that selected Vulkan device. This can test whether moving browser rendering away from the iGPU changes recurrence, but does not guarantee every browser GPU path uses Mesa or prove the iGPU is faulty. Source: [Mesa environment variables: `DRI_PRIME`](https://docs.mesa3d.org/envvars.html#envvar-DRI_PRIME).
- **There is no primary-source basis to name a fixed regression version.** Hyprland v0.55.4 is the immutable commit [`a0136d8`](https://github.com/hyprwm/Hyprland/commit/a0136d8c04687bb36eb8a28eb9d1ff92aea99704); its release notes list small backports, including a renderer monitor-disconnect SEGV fix, but no AMDGPU ring-timeout or reset-recovery fix. Its build metadata accepts Aquamarine `>=0.9.3`, so installed Aquamarine 0.11.0 meets the declared minimum but that does not establish compatibility with this failure mode. Sources: [v0.55.4 release](https://github.com/hyprwm/Hyprland/releases/tag/v0.55.4); [v0.55.4 CMake dependency declaration](https://github.com/hyprwm/Hyprland/blob/v0.55.4/CMakeLists.txt#L94-L108).

## Decision implications
- **Supported diagnosis:** one observed AMDGPU graphics-ring hang occurred on the Raphael iGPU (`0000:14:00.0`), associated with a browser GPU worker; the kernel recovered via MODE2, after which the graphical session failed. Treat the browser as an associated workload, not the proven culprit, and do not diagnose the RX 9060 XT from this event.
- **Lowest-risk next diagnostic:** make no configuration change. If it recurs, retain a narrow, read-only window of the kernel journal from before the first timeout through recovery, plus `lspci -nnk` and `/dev/dri/by-path` mappings. Record the PCI address, ring, reset outcome, GPUVM/page-fault lines, firmware/RAS/PCIe errors, and whether the dGPU (`0000:03:00.0`) appears. Do not key evidence or configuration to `cardN`.
- **Optional, reversible mitigation after that baseline:** change only the browser launch for normal use, either by disabling its hardware acceleration or by launching it once with `DRI_PRIME=pci-0000_03_00_0`. Compare ordinary-use recurrence and journal PCI addresses; revert if it does not help. This leaves the compositor device policy unchanged.
- **Keep compositor selection separate.** If evidence repeatedly implicates the iGPU and a compositor experiment is warranted, Hyprland documents `AQ_DRM_DEVICES` as an ordered allowed-device list. Make that a separate, deliberate test using stable PCI-derived udev symlinks and including any GPU that owns an attached display; it is not a safe inference from this single incident.
- **Do not change kernel reset parameters as a first response.** AMDGPU exposes `reset_method`, `gpu_recovery`, and debug/reset-mask controls, but its documentation labels these as driver controls/debugging features; forcing them would alter recovery behavior rather than identify the hang. Sources: [AMDGPU module parameters](https://docs.kernel.org/gpu/amdgpu/module-parameters.html); [AMDGPU debugfs](https://docs.kernel.org/gpu/amdgpu/debugfs.html).

## Gaps
- The narrow surrounding kernel journal and Hyprland renderer stack were inspected, but there is no reproducible trigger, browser/Mesa root-cause backtrace, GPU dump analysis, or temperature/power/firmware telemetry sufficient to identify the underlying defect. The cited upstream v6.18 source explains the mechanism, not an exact-version regression diagnosis for the installed 6.18.52 kernel.
- The exact browser rendering backend and actual GPU chosen at the time are unknown; the browser thread in the timeout record is association, not proof of rendering API or culpability.
- One recovered event cannot distinguish a kernel/Mesa/compositor/browser regression from firmware, PCIe, power, memory, or hardware instability, and no official source identified a fixed version for this signature.
